Filing Copilot — how you'd evaluate it

evals · conceptual walkthrough

This is how you'd evaluate the filing agent — the concept, not the code. The agent routes each question to RETRIEVE (answer from a cited section) or ANALYZE (compute a table in a sandbox, cited to the source). Evals are how you know it's still doing that correctly, question after question.

1Why evals

?

You can't ship on "looks right"

The agent is non-deterministic — the same question can route differently or word an answer differently on two runs. And it makes the two claims that are easiest to get subtly wrong: it states numbers and it cites sources. A demo that reads well can still route to the wrong path, cite the wrong Item, or report a margin that doesn't recompute. Evals turn "seems fine" into a measurable gate — a suite that passes or fails on thresholds, run before every change and on live traffic.

2What to evaluate — the four surfaces

Each answer passes through the same four decision points. Evaluate each one on its own so a failure tells you where it broke.

ROUTING

Right path?

Did the router pick retrieve vs analyze as expected — and pick the right Item / dataset / skill within that path?

"trend in margin" must go analyze, not retrieve.
RETRIEVAL GROUNDING

Faithful to the section?

Is the answer supported by the cited section's text, and is that citation the correct Item — not a plausible-looking wrong one?

Risk-factor answer must cite Item 1A, not Item 7.
ANALYSIS CORRECTNESS

Numbers recompute?

Do the sandbox's numbers independently recompute from the source dataset? Right skill + dataset? Did the sandbox run cleanly and return a valid result?

32.0% must equal op_income ÷ revenue on income_statement.
ANSWER QUALITY

Actually answers?

Does the final response address the question — relevant, complete, and not dodging with a technically-true non-answer?

"how has it trended" needs a direction, not just a table.

3Grader types — the craft point

The whole game is choosing the strongest grader each surface will bear. Prefer a deterministic check over a judge for anything numeric — if you can recompute it, don't ask a model to eyeball it.

GraderHow it scoresUsed for (this system)
DETERMINISTIC
strongest — use wherever possible		 Code checks the answer against ground truth. No model in the loop, so it's exact and repeatable. Recompute the metric from the source dataset & compare · citation resolves to a real Item/table · units & periods match ($M, FY) · sandbox result schema valid · routing == expected
LLM-AS-JUDGE
for the fuzzy parts only		 A strong judge model scores against a written rubric, calibrated against human labels so its scores are trusted. Faithfulness — every claim traces to the retrieved section text · relevance / completeness — does it answer the question
STRUCTURAL / TRACE
from the trace, free		 Assertions over the response trace — which path ran, whether it errored, how long it took. Which path executed · sandbox ran clean vs errored · latency within budget · a fallback plan didn't silently fire
✓

Deterministic beats judge for numbers

A margin is right or wrong — you have the source table, so recompute it and compare to a tolerance. Save the judge for faithfulness and relevance, where there's no closed-form answer. A judge that grades numbers is slower, costs tokens, and can be talked into a wrong "looks fine."

4Single-turn evals

One question → one answer, scored independently. This is the bulk of the suite: a curated case set where each case knows its expected route, expected citation, and (for analyze) the recomputed ground-truth numbers.

▣

Where it runs

The same cases run in two places: as an offline suite / CI gate before any prompt or skill change ships, and against sampled production traffic — where the deterministic checks (recompute, citation-resolves) still work live, since the source table is right there.

5Multi-turn evals

A real session is a conversation — follow-ups that drop the company name, pronouns that point at the last table, comparisons that assume prior turns. You evaluate a scripted trajectory: a fixed sequence of turns, scored per-turn and as a whole.

T1
What's Apple's operating margin trend?
→ analyze · income_statement · margin expanded 30.3% → 32.0%
Item 8 · Income Statement (XBRL)
T2
And gross margin?
→ analyze · same filing · gross margin trend
must reuse the same filing + context — no "which company?"
T3
Is that better or worse than revenue growth?
→ compares this turn's figures against T1/T2 results
must reference prior turns' numbers, not recompute a contradiction

The checks single-turn can't catch — these only exist across a conversation:

Context retention

Carries the filing + prior results forward. Doesn't re-ask "which company?" or lose scope on T2.

Consistency

Later turns don't contradict earlier numbers or claims — T3 uses the same 32.0% it said in T1.

Grounding maintained

Every turn still cites / recomputes. No drift into ungrounded assertions as the chat gets longer.

Trajectory / goal completion

The multi-step task actually finishes — by T3 the comparison the user was building toward is delivered.

No hallucination accumulation

A small error on T1 doesn't compound into a wrong conclusion on T3. Errors don't snowball.

↻

Method

Fixed conversation scripts, replayed turn by turn. Each turn gets the same per-turn deterministic + judge checks from §4 (route, recompute, citation, faithful). Then a trajectory-level judge reads the whole transcript and scores retention, consistency, and goal completion — the things you can only see across turns.

∞

Self-improving

The agent's own failures are the best test cases. Every production miss that gets diagnosed is promoted into the eval set — so the suite grows toward exactly the questions this agent gets wrong, and each fix is locked in by a regression case.
